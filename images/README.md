# 基础镜像维护手册

算子开发者可直接采用已发布的精确版本，见[基础镜像的选择与开发](../docs/DEVELOPMENT_AND_CI.md#基础镜像的选择与开发)。本手册用于新增、验收、发布和恢复基础镜像。构建端从 Harbor 拉取，最终算子镜像继续按算子流水线同步 ACR。

## 新增配方

每个目录对应一个 Harbor 仓库，每个系列独立维护版本。

| 文件 | runtime | 专用 builder |
|---|---|---|
| 配方目录 | `images/runtimes/<name>/` | `images/builders/<name>/` |
| `VERSION` | 单行精确版本，首版 `1.0.0` | 同规则，独立升版 |
| `Dockerfile` | 选择受控上游系统镜像并固定内容 | 使用已发布的 `.../base/runtime/<name>:X.Y.Z`，在该环境上安装工具链 |
| `check.sh` | 以 UID 10001 在目标镜像中检查解释器、运行库及实际功能 | 在父 runtime 中执行并验证样例产物 |
| `check-build.sh` | 无需提供 | 在 builder 中将最小编译样例输出到 `/sample`，供 `check.sh` 只读访问 |

目录名称使用小写字母、数字及连字符。基础环境以 `linux/amd64` 构建，容器验收禁网、根文件系统只读。新配方无需先登记消费方。新增 builder 之前应先发布其父 runtime。修改现有系列的 Dockerfile、工具输入或验收契约时一并提高 `VERSION`。仅修改算子依赖锁通常无需更新基础镜像。

从仓库根目录运行；以下使用仓库的 CPU runtime 作为示例：

```bash
python3.12 -m ci.base_images.manage check --recipe runtime/python312-cpu
```

## 发布与读取

1. 将配方和版本提交 MR。`check-base-images:<配方>/<版本>` 按计划验证受影响配方，失败时用同一组本地命令复现。
2. 合入受保护的 `develop` 后，`build-base-images`、`test-base-images`、`publish-base-images` 自动处理变更系列。首次发布新镜像时，作业使用验收过的镜像内容创建精确版本，随后使同系列的 `:dev` 指向相同摘要。构建先上传现有仓库的 `<版本>-ci.<父流水线>.<构建作业>`；验收按摘要拉取，发布仅创建已验收版本标签。
3. 从 `build/base-images/<配方>/<版本>/publish/<job_id>/receipt.json` 读取系列、版本、仓库、目标平台、源码提交、配方树、流水线编号和镜像摘要；builder 另含父 runtime 的引用及摘要。以 `repository:version` 写入算子 Dockerfile。临时本地测试可用 `repository:dev`。
4. 合入 `main` 时核对 `develop` 的发布回执、版本标签和配方来源。发布提交须为 `main` 的祖先（快进或保留该提交的合并）。基础镜像不会再次发布。已有算子运行的是自己的镜像；要采用新的基础版本，应由相应的算子版本单独修改 Dockerfile 并验收。

例如 CPU runtime 第一个版本的目标地址为 `harbor.striding.internal/data/data-operators/base/runtime/python312-cpu:1.0.0`。仓库端的长期版本回执使用同一仓库中的 `receipt-1.0.0`。历史 `tested-<源码提交>` 标签保留；新构建的临时标签只用于 CI 交接。算子始终使用数字版本。

## 发布权限与失败处理

基础镜像发布使用 Harbor 现有配置。受保护的发布作业按镜像系列串行执行，为每个精确版本保存一份长期回执，已有版本只接受同一制品。构建端用 Docker Buildx 按摘要读取回执，核对仓库、版本和当前版本标签的摘要，再按摘要构建。发布后回读精确版本与 `:dev`。保留精确版本、回执和恢复制品，把同仓库的写权限限定在受信任的发布者；拥有写权限的其他账号仍可在 CI 外修改标签。

| 情况 | 处理 |
|---|---|
| 发布中断 | 生产镜像和测试证据仍有效时，重试发布作业以补齐精确标签或 `:dev`；重建导致作业 ID 或摘要变化后必须重新验收。整个子流水线重建须启动新父流水线。 |
| 同一精确版本指向不同内容，或配方来源不匹配 | 作业失败。核对原回执，用新版本发布修复，不覆盖原标签。 |
| 更高版本已经发布 | 旧提交不能将 `:dev` 回退。消费方需要回退时，在自己的 Dockerfile 恢复原精确版本。 |
| 发布标签与长期回执摘要不符 | 停止消费或发布，核对原始回执和源提交。发布修复时使用新版本。 |

完整的职责、阶段和迁移边界见[基础镜像管理与发布方案](../docs/FOUNDATION_IMAGES.md)。

新 runtime 必须先独立发布，再提交引用它的 builder 或算子；计划冻结时解析已发布父镜像，不以同一流水线尚未发布的标签作为基础。release/main 在父流水线中只读核对已有回执和祖先提交，不重建基础镜像。
